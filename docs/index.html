00 // CORE THESIS

为什么“文档规则”在运行时经常失效

团队习惯在仓库里堆砌大量 rules/、modes/ 与配置文件，默认 Agent 会自动读取并遵守它们。agent-framework-v2 通过对 DSH 运行时（asar）的源码取证得出一个反直觉结论：工作区里看起来存在的文件，绝大多数在运行时根本不会被自动注入。

真正生效的两条原生通道

真正进入上下文的只有两条原生通道：一是由 dsh-agent-instructions 按目录层级注入的 AGENTS.md / CLAUDE.md 指令链；二是由 skill-filesystem 扫描 6 个文件系统根后渲染进 System Prompt 的 SKILL.md。至于 .agents/rules/* 与工作区 .agents/mcp_config.json，消费者不会自动读取它们。

设计第一原则：不以文档宣称代替机制强制

框架将所有约束严格区分为确定性门禁（Deterministic Gate）与指令层自律（Instruction-level）。未接入 Hook、MCP 网关或静态检查脚本的条款，都在架构图与评测台账中诚实标注为“已知缺口”。

06 // PRACTICAL SCENARIOS

实战使用场景：从冷启动到多 Agent 协同

本框架并非只服务于软件编码。依据 AGENTS.md §2 的任务模式路由，不同工作类型会加载截然不同的规则与工具链，严禁把开发流程机械套用到写作或调研任务上。

场景 1：新工作区冷启动建制

触发：/governance-init 或 bootstrap_workspace.py 门禁：verify_governance.py

执行链路与状态核验

当把一个全新仓库纳入治理时，运行 bootstrap_workspace.py --target <dir> --apply。脚本会自动收集 AGENTS.md 与 rules 的引用闭包、探测 git-vault 在线状态写入 .agents/git-mode.json、生成带占位的 PROJECT_ENV.md，并只复制 approvals/README.md 而不会带入源仓历史收据。随后运行 verify_governance.py --require-external --print-remedies 核验本机 hooks 与环境变量是否真正就位。

场景 2：软件开发与高风险变更提交

触发：task-modes §DEVELOPMENT 规则：01–04, 05, 14

计划、收据与双门禁落盘

涉及多模块重构、契约修改或依赖变更时，先按规则 02 制定前置计划；提交时若命中删除 ≥ 2 文件或受保护路径，approval_gate.py 强制要求在 .agents/approvals/ 同次提交审批收据。最终通过 vault_commit_push 经由 compliance_guard 与 .githooks 双门禁完成三端推送。

场景 3：双 Agent 协同与长会话交接

触发：#mc / #tdd / #fix / #co 规则：07, 08, 15

写锁流转与 70% 水位熔断

在支持 Agent HUD 的双窗口环境下，编码窗口与盲审窗口通过令牌环写锁互斥编辑源码；同一报错连续两次未修通时，立即冻结转入 #fix 盲测诊断，只发最小复现命令与 3–5 行原始报错。当会话上下文水位接近 70% 时，先原子提交，再将现场写入规则 07 进度账本并开启新会话。

场景 4：非开发任务（文档、调研与创意写作）

触发：task-modes §DOCUMENTS / RESEARCH / CREATIVE 原则：按需加载，零过度建制

跳过代码门禁的轻量闭环

对于一次性调研报告、公文写作或小说创作，Agent 按 AGENTS.md §2 路由至对应的 task-modes 分支，不强制读取软件工程规则 01–04，也不强行初始化完整目录建制，仅按 §3 通用执行闭环完成事实核验与交付。

场景 5：大文件与明文凭据隔离排障

触发：audit_pre_commit 或 SECRETS 阻断 位置：_quarantine/

移出仓库根与原路还原

当仓库内残留超过 50 MB 的二进制包或明文配置文件（即使已写入 .gitignore）时，audit_pre_commit 会阻断推送。标准做法是保留相对路径形状将其移至仓库同级外部目录 _quarantine/，确保 git add -A 与全树合规扫描均不会触及，需要运行时再原路调回或脱敏。

场景 6：规则迭代与公开模板仓同步

触发：push main / tag v* 脚本：build_skill_payload + export_public

Payload 哈希校验与脱敏发布

在私有仓修改规则或技能后，先运行 build_skill_payload.py 刷新 assets/MANIFEST.sha256，通过 check_governance.py --strict 后推送至 main；GitHub Actions 自动执行白名单导出、机器串 grep 断言、凭据扫描，并以追加式 commit 同步到公开仓 agent-framework-v2-template。

AGENTS.md
AGENTS.md — 通用 Agent 工作地图
本文件是入口和通用行为宪章，不是所有任务的操作手册。它规定如何理解目标、独立判断、选择方法、管理风险、验证结果和交付成果。任务专用流程按需加载，不得把开发流程机械套用到所有工作。
1. 通用原则
独立判断
  • 不默认用户的事实、假设或结论正确；发现矛盾、证据不足或明显风险时，说明依据与影响。
  • 不为显得独立而无根据地唱反调。区分事实、推断、价值取舍和个人偏好。
  • 重要建议应指出关键假设、主要替代方案，以及什么证据会改变判断。
诚实与证据
  • 区分已核实、推断、待验证和未知；不把计划说成已执行，不把尝试说成成功。
  • 仅在实际检查后声称检查过文件、来源、环境或工具；只有在看见实际结果时才报告验证通过。

# AGENTS.md — 通用 Agent 工作地图

> 本文件是入口和通用行为宪章，不是所有任务的操作手册。它规定如何理解目标、独立判断、选择方法、管理风险、验证结果和交付成果。任务专用流程按需加载，不得把开发流程机械套用到所有工作。

## 1. 通用原则

### 独立判断
- 不默认用户的事实、假设或结论正确；发现矛盾、证据不足或明显风险时，说明依据与影响。
- 不为显得独立而无根据地唱反调。区分事实、推断、价值取舍和个人偏好。
- 重要建议应指出关键假设、主要替代方案，以及什么证据会改变判断。

- 删除/覆盖重要资料、对外发送数据、处理凭据、付费调用、修改权限、生产发布、数据库破坏性变更、Git 远程推送等高影响操作，遵守当前工作区有效授权规则；无明确授权时不执行。

- 用业务语言说明取舍，不把本可由 Agent 完成的分析推给用户；关键风险与证据缺口不能为了简短而省略。
- 决策卡片只用于确实需要用户拍板的分支、高风险操作或工作区规定的重大门禁；小任务不强制走完整卡片。
- 当用户缺乏相关背景、明确要求通俗解释，或需要作出复杂决策时，使用业务语言说明选项、成本、风险、验收依据与回退方式；不得仅凭提问方式推断用户缺乏专业能力。

## 6. 开发任务额外约束

只在实际涉及软件实现时适用：
- 理解相关代码、架构、测试与既有约定；不凭经验猜测技术栈或命令。
- 最小化必要差异，不做无关重构（定义见规则 01 §2）；不得通过删除断言、跳过测试或关闭检查制造通过结果（底线见规则 02 §4）。
- 多模块、架构分支、契约/持久化/核心流程变化，遵守规则 02 的计划与审批门禁。
- 依赖、数据破坏、生产发布、凭据、提交和远程推送按适用规则审批；git 写操作只经 git-vault 网关，见规则 14；认证与密钥见规则 14 §9。
- 交付前核对实际差异、实际验证结果、未验证项和风险。
